01架构与选型决策

四个决定了后续一切成本的选择

决策一：单文件 HTML，不上构建

整个站点是一个 index.html：内联 CSS、内联 JS、零外部脚本。理由不是"偷懒"，而是三个具体约束：

  • 可双击打开——朋友拿到文件夹就能看，不需要 npm install、不需要 vite dev；
  • 托管零配置——任何静态服务器把目录一丢就能跑，发布流程只有"上传"一步；
  • 没有构建期就没有构建期故障——不会出现依赖版本漂移、node_modules 体积、CI 缓存失效这类问题。

代价是作用域污染。解法是用 IIFE 手动切模块：每一块独立功能都包在立即执行函数里，只在 window 上留必要的一个钩子。 

JS 模块切分/* 每一段功能 = 一个 IIFE，变量随函数执行结束离开作用域 */
(function(){
  const io = new IntersectionObserver(entries => { /* ... */ }, {threshold: .15});
  document.querySelectorAll('.reveal').forEach(el => io.observe(el));
})();

(function(){
  const track = document.getElementById('ticker-track');
  /* ... */
})();

唯一跨模块的耦合点是启动顺序：开机动画结束后要主动调用 startTyped()， 所以它以函数声明（而非 IIFE）暴露在全局，其余全部封闭。

决策二：不用框架，用原生 API

页面的"动态性"其实只有四类需求，原生 API 全部覆盖，引入框架反而是净负担：

需求原生方案为什么不用框架
滚动到视口触发动画IntersectionObserver比 scroll 监听省一次重排，且是浏览器原生调度
逐帧跟随（光标、数字滚动）requestAnimationFrame需要精确控制每一帧，虚拟 DOM 无能为力
一次性突发动画（全局故障）element.animate()（WAAPI）命令式、不污染 CSS、自动销毁
状态切换（面板/弹窗/菜单）classList.toggle + CSS 过渡状态只有开/关两态，不需要响应式系统
判断标准

是否引入框架，看的是「状态派生关系的复杂度」，不是「页面酷不酷」。这个页面所有状态都是单点布尔值，派生关系为零，所以原生足够。如果要做多视图路由 + 数据驱动的列表渲染，结论会立刻反转。

决策三：内容收进一个 CONFIG 对象

文案、代号、语录、文章列表、义体数据全部集中在 CONFIG。这样做的好处是改内容不用碰结构—— 后来瑞哥自己把代号改成「张瑞.」、把「网络黑客」整篇换成「高塔晚风」，都只需要动这个对象里的几个字段。 

JS 配置结构（节选）const CONFIG = {
  callsign: '张瑞.',
  handle:   '瑞哥. TERMINAL',
  typedLines: [ '...', '...' ],      // 打字机循环的句子
  posts: [                                        // 超梦档案 = 博客卡片
    { tag:'高塔晚风', date:'2077.08.03', videoKey:'tower',
      title:'夜之城没有真东西，她不一样', excerpt:'...' }
  ],
  cyberware: [ /* 义体条目：名称/等级/描述 */ ],
  tickerItems: [ ['NCPD 通缉', '...'] ]
};

决策四：源码与产物分离（后期补的）

压缩 HTML 之后必须保留可读版本，否则后续维护等于在压缩代码上做手术。 最终目录是 src/index.source.html（可读源码）+ index.html（构建产物）+ 一个 40 行的构建脚本。 这个决策的副作用在第 6 节会讲——它制造了一个「改哪份」的陷阱。

02视觉系统的实现

赛博朋克不是"加点霓虹"，而是一套可复用的色彩、字体、噪声语言

2.1 设计令牌：先把颜色定死

所有颜色走 CSS 自定义属性，一处改全局生效。CP2077 的标志性黄（#FCEE0A）是低明度高饱和的黄， 它只能在深色底上大面积使用；一旦挪到浅色底就会直接失明——这也是这份笔记没有沿用它的原因。 

CSS:root{
  --yellow:#FCEE0A;   /* 主强调：标题、HUD 边框 */
  --cyan:#00F0FF;     /* 次级：数据、扫描线、链接 */
  --red:#FF003C;      /* 警告 / 故障红通道 */
  --pink:#FF2E88;     /* 点缀：广告牌、标签 */
  --bg:#04060A;       /* 近黑，带一点蓝，不是纯黑 */
  --panel:rgba(8,13,20,.82);  /* 半透明面板，让噪点透出来 */
  --line:rgba(0,240,255,.18);  /* 细边界，比实色柔和 */
  --text:#D8E4EC;      /* 冷白，不用 #fff（太刺） */
}
技术点

背景用 #04060A 而不是 #000：纯黑会让霓虹边缘显得"漂浮"，带一点蓝的近黑能给辉光提供"底色的厚度"，同时降低 OLED 屏上的拖影观感。

2.2 字体三层结构

层字体用途回退策略
展示层Orbitron代号、大标题、数字断网时回退到 PingFang SC / 系统等宽，风格打折但可读性不塌
界面层Rajdhani正文、导航、按钮
数据层Share Tech MonoHUD、时间码、终端输出

这是刻意的三档而不是两档：等宽字体负责"机器感"，无衬线负责"可读性"，展示字体负责"识别度"。 三者混用形成了 CP2077 那种"军用设备 + 商业广告"的错位感。

2.3 RGB 色差故障字：两个伪元素 + clip-path 切片

这是全站最核心的视觉母题。实现上没有用任何图片或 shader，纯粹是两层伪元素叠在文字背后， 分别染成青色和红色，然后用 clip-path: inset() 裁成横向条带、做微小位移。 

CSS — 故障字核心.glitch{position:relative; display:inline-block}

.glitch::before{  /* 青通道 */
  content:attr(data-text);
  color:var(--cyan); z-index:-1;
  animation:gl-a 3.2s infinite steps(1);
}
.glitch::after{   /* 红通道 */
  content:attr(data-text);
  color:var(--red); z-index:-2;
  animation:gl-b 2.7s infinite steps(1);
}

/* 关键帧：88% 之前完全静止，89%~95% 突然切三次条带 */
@keyframes gl-a{
  0%,88%,100%{transform:translate(0); opacity:0}
  89%{transform:translate(-4px,2px); clip-path:inset(10% 0 55% 0)}
  91%{transform:translate(3px,-1px);  clip-path:inset(60% 0 8% 0)}
  93%{transform:translate(-2px,0);   clip-path:inset(30% 0 40% 0)}
  95%{opacity:0}
}
技术点为什么这么做
steps(1) 而非 ease故障的本质是瞬间跳变。加缓动就变成"抖动"，立刻从数字故障变成廉价动画。
0%,88% 长时间定格故障要稀缺才有冲击力。持续故障 = 视觉噪声，用户会开始忽略它。
clip-path: inset()做出"横向扫描线撕裂"的形状，比单纯位移更像信号损坏；且不影响布局盒模型。
两层而非一层青 / 红两通道错位 = 色差分离（chromatic aberration），这是 CRT 与廉价镜头的物理特征，比"单色重影"真实得多。
两个不同周期（3.2s / 2.7s）周期互质，合成后的故障节奏永不重复，避免用户产生"每 3 秒一次"的规律感。

还有一个交互层：:hover 时把周期压到 .4s / .35s。 鼠标移上去，故障从"偶发"变成"高频"——这是给可交互元素加的可点击性提示，不靠下划线、不靠颜色变化。

2.4 CRT 扫描带：一条会走完全屏的亮带

CSS.fx-crtbar{
  position:fixed; left:0; right:0; height:120px;
  pointer-events:none;   /* 绝不拦截鼠标 */
  z-index:9001;
  animation:crtbar 7s linear infinite;
}
@keyframes crtbar{ 0%{top:-15%} 100%{top:110%} }
技术点

起止位置要出界（-15% → 110%）而不是 0 → 100%。 否则亮带在屏幕边缘会"凭空出现/消失"，破坏运动的连续性；出界 15% 让它从画外滑入、滑出画外。 另外 pointer-events:none 是全屏特效层的硬性要求，漏了这个整站就点不动了。

2.5 胶片噪点：必须动起来，否则只是"脏"

噪点用内联 SVG 的 feTurbulence 生成，作为 data URI 平铺。但静态噪点会被眼睛识别为"图片质量差"， 所以关键在每 0.45 秒跳一次位置： 

CSS.fx-noise{
  background-image:url("data:image/svg+xml,...feTurbulence baseFrequency='.8'...");
  opacity:.055;
  animation:noiseShift .45s steps(3) infinite;
}
@keyframes noiseShift{
  0%  {transform:translate(0,0)}
  33% {transform:translate(-2%,1%)}
  66% {transform:translate(1%,-2%)}
  100%{transform:translate(0,0)}
}
参数取值理由
不透明度.055超过 .1 就看得见颗粒形状，从"胶片"变成"低画质"
steps(3)3 帧模拟胶片 24fps 下的颗粒跳动；连续位移会变成"飘动的纹理"
位移幅度1~2%大于 3% 会有明显的"图层在滑"的破绽

2.6 鼠标视差：6% 的 overscan 是硬要求

JSconst img = document.getElementById('hero-img');
addEventListener('mousemove', e => {
  const dx = (e.clientX / innerWidth  - .5) * 14;   // ±7px
  const dy = (e.clientY / innerHeight - .5) * 10;   // ±5px
  img.style.transform = `scale(1.06) translate(${-dx}px,${-dy}px)`;
});

scale(1.06) 不是装饰，是位移留出的余量：图片放大 6%（1920px 图 ≈ 115px 余量）远大于最大位移 7px， 所以画面永远不会露出容器底色。少了这个 scale，鼠标移到边角就会看到一条白边——这是所有"视差首图"最常见的翻车点。

另外位移方向取反（-dx）：鼠标右移，画面左移，形成"镜头在物体前面"的深度感。 同向移动会变成"画面跟着鼠标走"，更廉价。

2.7 光标光晕：lerp 插值，以及它的已知局限

JSlet gx = innerWidth/2, gy = innerHeight/2, cx = gx, cy = gy;
addEventListener('mousemove', e => { gx = e.clientX; gy = e.clientY; });

(function loop(){
  cx += (gx - cx) * .08;          // 线性插值：每帧靠近目标 8%
  cy += (gy - cy) * .08;
  glow.style.left = cx + 'px';
  glow.style.top  = cy + 'px';
  requestAnimationFrame(loop);
})();
已知局限

这个 0.08 是帧率相关的：60Hz 屏上每秒收敛 4.8 倍，120Hz 屏上会快一倍，观感不一致。 更严谨的写法是按帧间隔做指数衰减： k = 1 - Math.pow(1 - 0.08, dt / 16.67)，dt 取 requestAnimationFrame 回调的时间戳差。 这一版没改，因为拖尾效果差异在这个视觉强度下不可感知——但这是个值得记下来的正确做法。

03交互动效层

五个小机制，决定页面是"能看"还是"好用"

3.1 开机自检序列：幂等的 finish()

首屏是一段 "WAKE UP, 瑞哥_" 的神经链路自检。它有三个出口：逐行走完、点击跳过、3.4 秒兜底超时。 三条路径都能触发 finish()，所以必须幂等，否则打字机会被启动两次、滚动锁会被提前释放。 

JSlet done = false;
const finish = () => {
  if(done) return;        // ← 幂等守卫，整个机制的核心
  done = true;
  boot.classList.add('done');
  document.body.style.overflow = '';   // 解锁滚动
  startTyped();
};

const timer = setInterval(() => {
  if(i >= seq.length){ clearInterval(timer); bar.style.width = '100%'; setTimeout(finish, 550); return; }
  /* 逐行追加，进度条封顶在 92% —— 最后 8% 留给"收尾"动作 */
  bar.style.width = Math.round(((i+1)/seq.length) * 92) + '%';
}, 300);

boot.addEventListener('click', finish);   // 出口 2：点击跳过
document.body.style.overflow = 'hidden';         // 先锁滚动
setTimeout(finish, 3400);                        // 出口 3：兜底
细节用意
进度条封顶 92%真实进度条不会"走满才算完"，最后一段必须由完成事件补齐。这一下就把"假加载"演成了真的。
锁 body.overflow开机层是全屏 fixed，但底下页面仍在滚动上下文里。不锁会出现在动画期间已经滚到中间的诡异状态。
3.4s 兜底如果某一行数据异常导致循环不结束，用户会被永久锁在黑屏。任何全屏遮罩都必须有一条超时逃生路径。

3.2 打字机：节奏不能均匀

JSif(!deleting){
  el.textContent = line.slice(0, ++ci);
  if(ci === line.length){ deleting = true; setTimeout(tick, 2400); return; }  // 打完停 2.4s
  setTimeout(tick, 55 + Math.random()*60);      // 55~115ms 随机
} else {
  el.textContent = line.slice(0, --ci);
  setTimeout(tick, 22);                            // 删除固定快
}

三个节奏参数各自有理由：打字随机（人手不是节拍器）、删除固定且更快（回退是机器动作）、 打完停顿 2.4 秒（给读者读完的时间）。全用同一个 interval 会立刻显出"程序在循环"。

3.3 滚动驱动：IntersectionObserver 双阈值

JS// 入场显现 + 属性条填充：阈值 .15
const io = new IntersectionObserver(entries => {
  entries.forEach(e => {
    if(!e.isIntersecting) return;
    e.target.classList.add('in');
    e.target.querySelectorAll('.bar i').forEach(b => {
      b.style.right = (100 - parseFloat(b.dataset.w)) + '%';
    });
    io.unobserve(e.target);          // 只触发一次
  });
}, {threshold: .15});

// 数字滚动：阈值 .5，必须先看到一半才开始数
const p = Math.min((t - t0)/dur, 1);
el.textContent = Math.round(target * (1 - Math.pow(1-p, 3))).toLocaleString();  // easeOutCubic
技术点

unobserve 是必需的。不加的话每次滚动进出都会重跑动画，用户上下滑动时数字会反复跳到 0 再数上去，非常廉价。
阈值差异也有效：显现用 .15（露一点就开始，避免"滑过去了才出现"的空窗）；计数用 .5（数字必须进视口一半再跑，否则用户看不到起始值，滚动感变成"突然变了个数"）。

另一处细节：滚动监听加 {passive: true}，告诉浏览器"我不会 preventDefault"， 浏览器就能把滚动交给合成线程，主线程卡顿不会拖住滚动。 

JSaddEventListener('scroll', () => {
  let cur = -1;
  secs.forEach((s,i) => { if(s && s.getBoundingClientRect().top < innerHeight*.4) cur = i; });
  links.forEach((a,i) => a.classList.toggle('active', i === cur));
}, {passive: true});

3.4 无缝跑马灯：复制一份内容

JS + CSSconst items = CONFIG.tickerItems.map(...).join('');
track.innerHTML = items + items;   // 内容复制一份 → 位移 -50% 时首尾严丝合缝

/* CSS 侧 */
.ticker-track{ animation:ticker 32s linear infinite }
@keyframes ticker{ to{ transform:translateX(-50%) } }
技术点

无缝滚动的通用解法：把轨道内容整体复制一遍，动画位移恰好等于原来那份的宽度。 因为复制后总宽翻倍，-50% 就等于一份的宽度，循环回到 0% 时视觉上完全连续。 这里用百分比而不是 px，所以内容多少、字体加载后宽度变化，都不会错位。

04超梦播放器（三代演进）

这个模块改了三次，每一次都是被一个具体问题推翻的

GEN 1 — 10.09
iframe 外链播放器 + 时长推算

用 B 站 player.html 内嵌，硬编码 duration: 61，靠定时器推算"播完"来触发结束特效。

GEN 2 — 10.10
发现问题：空白 + 出戏 + 状态不可知

嵌入环境下一片黑屏；播放器自带弹幕/推荐/分享 UI 严重破坏沉浸感；跨域 iframe 读不到播放进度，暂停时推算会漂移。

GEN 3 — 10.10 起
原生 <video> + 自绘 HUD + 注册表

视频落本地，用真 ended 事件驱动结束特效，进度条/时间码自己画，六个视频走配置注册。

4.1 为什么必须换掉 iframe

iframe 方案
  • 跨域，读不到 currentTime / duration
  • 播放状态只能靠外部定时器猜
  • 第三方 UI 无法移除（弹幕、推荐、logo）
  • 嵌入环境有加载黑屏风险
  • 用户暂停 → 推算的时间继续走 → 特效提前触发
原生 video 方案
  • 同源，全部状态可读可写
  • ended 事件 = 唯一可靠的播放结束信号
  • controls=false，UI 100% 自绘
  • 首帧加载通常更快（少一层播放器初始化）
  • 可以 playbackRate、muted 自由控制

4.2 全息投影的视觉构成

打开回放时看到的"投影仪"其实是四层独立元素叠出来的，没有用任何贴图：

层实现作用
光锥clip-path 梯形 + 纵向渐变从底部射向幕布的体积光
地面光斑椭圆 + blur + 低透明度青色让光锥"落地"，建立空间关系
幕布扫描线repeating-linear-gradient 1px 横线投影面的 CRT 质感
全息闪烁bdHoloFlicker：不规则透明度跳变"廉价投影仪在抖"的心理暗示

闪烁曲线是刻意不规律的——如果每 0.5 秒均匀闪一次，大脑会归类为"呼吸灯"； 只有长短不一的跳变才会被解读为"不稳定设备"。

4.3 结束投影特效：1.5 秒的 6 段时间轴

这是整个项目里技术含量最高的一段动画：视频放完的瞬间，幕布像被断电一样纵向塌缩成一条光带。 核心是 scaleY 从 1 压到 0，配合 transform-origin: bottom，并让亮度反向飙升来制造"能量被压缩"的错觉。 

CSS — 幕布塌缩#bd-player.ending .bd-frame{
  animation:bdHoloOut 1.5s cubic-bezier(.5,0,.75,0) forwards;
}
@keyframes bdHoloOut{
  0%  {opacity:1; transform:none; filter:none}
  16% {transform:translateX(-9px) scaleY(1.02); filter:brightness(1.7) saturate(1.4) hue-rotate(-8deg)}
  25% {transform:translateX(10px) skewX(-2deg);  filter:brightness(1.5) hue-rotate(12deg)}
  40% {transform:scaleY(.62) translateY(4px);   filter:brightness(2.5) opacity:.96}
  60% {transform:scaleY(.17) scaleX(1.03);  filter:brightness(3.6) blur(1.5px)}
  76% {transform:scaleY(.03) scaleX(1.08);  filter:brightness(5)   blur(1px)}
  100%{transform:scaleY(0)   scaleX(1.16);  filter:brightness(6.5) blur(3px); opacity:0}
}
时间画面技术手段
0 – 16%RGB 撕裂抖动translateX 正负跳变 + skewX 斜切 + hue-rotate 色相偏移
16 – 40%开始纵向压缩scaleY 1 → .62，同时 brightness 1.7 → 2.5
40 – 76%压成极窄光带scaleY .17 → .03，scaleX 略增（压缩守恒的视觉暗示），blur 加晕
76 – 100%白光爆闪后消失brightness 飙到 6.5 + blur(3px) + opacity 0
三个关键手法

① transform-origin: bottom——塌缩的锚点在底部，画面才会像"被投影仪收回"一样从下往上收，而不是从中心缩小（那看起来像"缩略图动画"）。
② 亮度与压缩量成反比——面积越小、亮度越高。物理上不通，但知觉上"能量被压进一条线"的暗示极强，这是所有科幻 HUD 断电特效的通用配方。
③ 缓动不是 ease——cubic-bezier(.5,0,.75,0) 是"慢起、后段猛烈加速"，模拟机械惯性而不是匀速收缩。

同一时间轴上还并行了四条独立动画（都锁 1.5s，靠 forwards 定格）：光锥与地面光斑淡出（bdBeamOut）、 HUD 上下栏延迟 30% 后淡出（bdHudOut）、底部白色光带横向拉伸（bdCollapse）、 以及"信号丢失"文字（bdEndFlash，36% 时以 letter-spacing: .3em 淡入，做出"扫描确认"的节奏）。

4.4 用真实 ended 事件，而不是算时长

JSvid.addEventListener('ended', end);   // ← 唯一可靠的"播完"信号

function end(){
  if(wiping) return;                  // 防重入：ended 与手动按钮可能同时触发
  wiping = true;
  const d = (vid && isFinite(vid.duration)) ? vid.duration : 0;
  if(vid){ try{ vid.pause(); }catch(err){} }

  player.classList.add('ending');       // 这一行触发全部 1.5s 动画
  setTimeout(() => {
    player.classList.remove('open', 'ending');
    mount.innerHTML = '';                 // 移除 video 元素 → 释放解码器
    vid = null;
    document.body.classList.remove('bd-open');  // 解锁滚动
    toast('// BD-CHIP 回放结束 · 全息投影已断开');
  }, 1560);                                // 比动画 1500ms 多 60ms，等最后一帧落定
}
设计选择原因
ended 而非 timeupdate 判 currentTime >= durationtimeupdate 触发频率约 4Hz，且末尾可能不触发；ended 是规范事件，一次且仅一次
wiping 布尔锁ended 和用户点「结束投影」可能在同一帧发生，不加锁会播两遍
1560ms 而非 1500ms动画最后一帧是 opacity:0，但合成层可能还有一帧残留；多给 60ms 避免"闪一下又出现"
移除 video 元素而非 pause()隐藏的 video 仍占解码器与内存；innerHTML='' 让 GC 能真正回收

4.5 自动播放：必须在手势调用栈里调 play()

JSvid = document.createElement('video');
vid.src = bd.src;
vid.preload = 'auto';
vid.controls = false;          // 用自家 HUD，浏览器控件全部关掉

浏览器策略

Chrome / Safari 只允许在用户手势的调用栈内启动带声音的媒体播放。若把 play() 放进 setTimeout、await fetch 之后、或 load 事件回调里，user activation 已失效，播放会被拒绝（NotAllowedError）。 这正是为什么 open() 里创建元素后立刻同步调 play()，而不是等 canplay。

playsinline 同理是硬要求：iOS Safari 上不声明它，视频会劫持全屏，整个全息投影框直接消失。 两套写法（属性和 setAttribute）都要给，因为老版本 WebKit 只认 webkit-playsinline，而新规范认 playsinline。

配套的是文件存在性探测：页面加载后对每个源发 HEAD 请求，只有确认存在才点亮「接入回放」， 否则保持不可点。这样"视频还没上传"的中间状态不会产生死链——用户点了黑屏，比按钮灰着糟糕得多。 

JS — 三级放行策略for(const a of links){
  const bd = BD_SOURCES[a.dataset.key];
  if(!bd) continue;

  // ① 本地 file:// 直接放行（该协议下 fetch 必然失败，见第 9 节）
  if(isLocalFile){ a.classList.add('ready'); continue; }

  try{
    const r = await fetch(bd.src, { method: 'HEAD' });
    // ② 只有明确「不存在」才锁住；405 / 403 / 500 一律放行
    if(r.ok || (r.status !== 404 && r.status !== 410)) a.classList.add('ready');
  }catch(err){
    // ③ 探测本身失败（跨域 / 离线 / file:）也放行
    a.classList.add('ready');
  }
}
为什么不是 if (r.ok) 就完事

HEAD 不是所有静态服务器都实现。部分服务器对 HEAD 返回 405 Method Not Allowed， 文件明明存在却被判定为"没有"。所以判定逻辑必须是黑名单（404/410）而不是白名单（200）—— 这是"渐进增强"在探测场景的具体形态：默认可用，只有确定不可用时才禁用。

4.7 生命周期：那个真实存在的空指针

播放器关闭时把 vid = null，但如果此时还有一帧 timeupdate 在队列里没执行， 回调里访问 vid.duration 就会抛 TypeError。表现是控制台红色报错 + 下一帧动画轻微卡顿。 

JS — 修复vid.addEventListener('timeupdate', () => {
  if(!vid) return;        // ← 守卫：元素可能已被移除
  const d = vid.duration || 0;
  if(d > 0){
    progEl.style.right = (100 - Math.min(vid.currentTime / d, 1) * 100) + '%';
    timeEl.textContent = fmt(vid.currentTime) + ' / ' + fmt(d);
  }
});
通用规则

凡是异步回调里引用了可被销毁的对象，回调第一行必须是空值守卫。事件监听不会因为元素被移除就自动注销—— 在 innerHTML='' 之后，绑定在元素上的回调仍可能因为已排队的任务而执行一次。

5.1 图片：PNG 换 JPEG + 限制最长边

Bash — macOS 自带 sipssips -s format jpeg -s formatOptions 85 -Z 800  portrait.png      --out portrait.jpg
sips -s format jpeg -s formatOptions 88 -Z 1920 hero-city.png     --out hero-city.jpg
sips -s format jpeg -s formatOptions 88 -Z 1100 cyberware-arm.png --out cyberware-arm.jpg
文件之前之后降幅关键动作
portrait（肖像）5.3 MB209 KB−96%最长边压到 800px
hero-city（首图）2.5 MB915 KB−64%1920px + q88
cyberware-arm（义体）1.5 MB419 KB−73%1100px + q88
技术点

① PNG 不适合照片。PNG 是无损格式，一张 1024×1024 的人像 PNG 里每个像素占 3~4 字节原始数据，压缩后仍有几 MB； JPEG 走 DCT 有损编码，同样观感只要几百 KB。只有需要透明通道或纯色图形时才该用 PNG。
② 分辨率上限比压缩质量更省。肖像在页面上最宽只显示约 400px，撑到 2 倍屏也只需要 800px。 把 2048px 的图压到 800px，比继续调 JPEG 质量参数省得多，且观感无损——因为多余的像素根本没被用到。
③ -Z 是"最长边"，不是宽或高。竖图横图都能正确约束，不会变形。

5.2 视频：ffmpeg 一组参数，逐个解释

BashFF=<ffmpeg 可执行路径>

$FF -y -i bd-frontend.mp4  -vf scale=1280:-2 \

参数作用为什么是这个值
-c:v libx264H.264 编码器浏览器/移动端/硬件解码全支持，兼容性天花板
-crf 22恒定质量（0–51，越小越好）18–28 是常用区间；22 偏保守，视觉上接近无损
-preset medium编码速度 / 压缩率折中slow 只多省 5~8% 但耗时翻倍，不值得
-pix_fmt yuv420p色彩采样 4:2:0兼容性硬要求：yuv444p / 10bit 很多浏览器不支持硬解甚至无法播放
-movflags +faststart把 moov 原子移到文件头否则必须先下完整个文件才能播；加了才能边下边播
-c:a aac -b:a 128k音频重编码128k 立体声是"透明"的经验值；视频里主要是人声与环境音
-vf scale=1280:-2缩放到宽 1280-2 不是 -1：H.264 要求宽高都是偶数，-2 会自动取最近的偶数

5.3 弃用 macOS 自带 avconvert 的原因

预设实测结果问题
PresetAppleM4VWiFi38MB → 2.5MB实际输出 480×272，画面糊成马赛克，不可用
PresetAppleM4V720pHD38MB → 19MB码率约 7.5Mbps，比源文件还高，压缩意义为零

avconvert 的预设面向"设备播放档位"（WiFi / 蜂窝 / HD），不暴露 CRF、码率、分辨率这些可控参数。 想精确控制压缩率就必须上 ffmpeg。这里还有一个环境坑：ffmpeg-static 从 GitHub 拉二进制在国内网络下会长期卡住， 改用 npm 源分发的 @ffmpeg-installer/ffmpeg 才能装下来（见第 9 节）。

为什么不用 clean-css level 2

实测只多省 1.5 KB，但 level 2 会合并重复规则、重构规则顺序，层叠优先级可能被改写。用 1.5KB 换整站样式错乱的风险，是负收益。

判断标准

压缩优化的收益必须相对于总传输体积评估。这个站 20MB 里视频占 18.7MB、图片 1.5MB、代码 0.06MB—— 在代码上再抠 2KB，用户感知为零。把力气花在体积最大的那一项上，而不是最容易动的那一项。

6.3 这个结构制造的新风险

发布确保产物是最新的，且与源码内容一致改完源码没构建就发布（线上还是旧版）

7.2 注入探针：验证事件到底有没有触发

"结束特效没出现"有两种可能：事件没触发，或者触发了但动画没生效。 不区分这两者，就会一直在错误的层里改代码。办法是挂一个探针：

  window.__ended = false;
  v.addEventListener('ended', () => { window.__ended = true; });
  return 'probe installed';})()`);

  endingCls: document.getElementById('bd-player').classList.contains('ending')})`);

探针一挂，结论立即清晰：__ended 一直是 false，说明事件根本没触发， 于是问题被定位到"视频没有真的播到结尾"，而不是"CSS 动画写错了"。

7.3 抓视频帧：不用截图，用 canvas

想确认"压缩后画质有没有下降"，需要看具体某一帧。用 CDP 的 captureScreenshot 在无头模式下抓 <video> 画面时会挂起不返回（合成层还没就绪）。改用页面内 canvas 直接读帧： 

JSconst c = document.createElement('canvas');
c.width = v.videoWidth; c.height = v.videoHeight;
c.getContext('2d').drawImage(v, 0, 0, c.width, c.height);
const dataUrl = c.toDataURL('image/jpeg', 0.8);   // 直接拿 base64，写入文件即可
前提

drawImage 要求视频同源，否则画布被"污染"（tainted），toDataURL 会抛 SecurityError。 本地视频天然满足；这也是当初放弃第三方播放器的又一个理由——跨域资源连"验证画质"都做不到。

7.4 四个把时间耗光的环境陷阱

现象真实原因正确做法
服务器/浏览器莫名"消失"，测试连不上 沙箱里后台子进程会随命令结束被回收 把起服务、起浏览器、跑脚本、杀进程写在同一条命令里
视频 seek 到结尾后又从 0 开始播 python3 -m http.server 不支持 Range 请求 不要用它测 seek；要测"播完"就改 playbackRate 加速跑完全程
CDP 连不上 /json/list Chrome 冷启动要 3~5 秒 轮询 /json/version 直到 200，而不是 sleep 4 硬等
npm install 报 ENOTEMPTY 上次 kill 掉的进程留下了半写状态 换一个全新的空目录安装，不要和残留的 node_modules 搏斗
Range 那个坑值得展开

HTTP Range 是"分段下载"能力，视频跳转（seek）依赖它。Python 的简易服务器对 Range 头直接忽略， 返回整个文件并给 200 而不是 206。浏览器拿到的数据从第 0 字节开始，于是 currentTime 被重置回 0。 表现就是"我明明跳到 59 秒了，怎么又从头发开始播"——看起来像代码 bug，其实是测试服务器能力缺失。 真实托管环境支持 Range，不受影响。

8.1 静态托管的形态

8.3 一次真实的"发布成功但线上是旧版"

中间出现过一次典型误判：多次修改都只在本地验证，线上链接一直是 首次发布时的快照。 症状是用户反馈"点视频打不开"，而在本地怎么测都正常。逐项对比后才发现线上那一版：

  • 「接入回放」是 onclick="return false" 的装饰性死链，根本没有播放器代码；
  • assets/bd-*.mp4 全部 404，视频文件从未上传；
  • 标题、图片都还是第一天的旧版本。
教训

"本地通过"只能证明代码是对的，不能证明线上是新的。 部署之后必须回读线上内容做一次断言——对比字节数、搜索特征字符串、逐资源查状态码。 这次就是因为没有做这一步，让一个不存在的功能被当成"已上线"了六天。

09踩坑清单

十二条，每条都真实发生过，附根因与修复

现象根因修复
双击打开，六个「接入回放」全点不动 file:// 协议下浏览器禁止 fetch，HEAD 探测全部抛异常，被当成"文件不存在"锁死 三重放行：本地协议直接放行、异常放行、只有 404/410 才锁
第三方播放器嵌进页面一片黑 跨域 iframe 在嵌入环境下的初始化失败，且外部完全看不到内部状态 放弃 iframe，视频落本地改原生 <video>
结束特效提前触发 / 不触发 用硬编码时长推算"播完"，用户暂停或缓冲时时序全错 改监听真实 ended 事件
关闭播放器后控制台报 TypeError 已排队的 timeupdate 回调在 vid = null 之后执行 回调首行加 if(!vid) return 守卫
带声音的自动播放被浏览器拒绝 play() 不在用户手势的调用栈内，user activation 已失效 在 click 处理器内同步调用，并 .catch() 兜住 NotAllowedError
iOS 上视频劫持全屏 未声明 playsinline，WebKit 默认全屏播放 同时写 playsinline 属性与 webkit-playsinline
服务端有文件却判定"没有" 部分静态服务器对 HEAD 返回 405 判定改为黑名单（只认 404/410），而不是白名单（只认 200）
跳到结尾后又从头播 python -m http.server 不支持 Range，currentTime 被重置 测试改用 playbackRate 加速，不用 seek
首图视差到边角露出白边 位移量超过了图片的冗余尺寸 容器加 scale(1.06) 做 overscan，覆盖率始终 > 位移量
数字滚动在上下滑动时反复重播 IntersectionObserver 未 unobserve，进出视口都触发 触发后 io.unobserve(target)，只跑一次
npm install 报 ENOTEMPTY 中断的进程留下半写的 node_modules 换全新空目录安装，不在残留目录里修
改了内容，线上还是旧的 "发布成功"被当成"内容生效"，从未回读验证 部署后 curl 首页 + 特征串 + 逐资源状态码做断言

一条贯穿始终的规律

十二条里有七条属于同一类：「我以为的状态」和「真实的状态」不一致。 iframe 里在播什么、ended 有没有触发、线上跑的是哪一版、file:// 下 fetch 能不能用—— 全部是"看不到内部"造成的误判。对应的解法也高度一致：把不可观测的东西变成可观测的 （探针、CDP 求值、回读线上内容）。

10可复用要点

下次做类似项目，直接抄这份清单

媒体播放器

  • 能用原生 <video> 就别嵌第三方播放器：状态可读、UI 可控、体积更小
  • 判断"播完"只用 ended，永远不要用时长推算
  • play() 必须在用户手势的同步调用栈内，且返回 Promise 要 .catch
  • 移动端必写 playsinline + webkit-playsinline
  • 关闭时 innerHTML='' 移除元素，而不是 pause() 后留着
  • 所有异步回调开头加空值守卫

渐进增强与探测

  • 资源存在性探测用黑名单（只排 404/410），不要用白名单（只认 200）
  • file:// 下 fetch 不可用，本地调试路径要单独放行
  • 任何"依赖网络探测才能启用"的功能，都要有探测失败时的兜底策略

CSS 动效

  • 数字故障用 steps(1)，加缓动就变成廉价抖动
  • 故障要稀缺：大部分时间静止，只在 1~2 帧里爆发
  • 两个不同周期叠加，节奏才不重复
  • 全屏特效层必加 pointer-events: none
  • 位移动画要出界（-15% → 110%），否则边缘会"凭空出现"
  • 塌缩类动画锚点在底：transform-origin: bottom + scaleY → 0
  • 压缩时同步提亮（brightness 反向上升），暗示"能量被挤压"
  • 视差图必须 overscan（scale > 1）覆盖位移量

性能

  • 照片用 JPEG，PNG 只留给图标和需要透明的图
  • 先限分辨率（-Z / scale），再谈压缩质量
  • H.264 + yuv420p + +faststart 是浏览器兼容的稳妥组合
  • CRF 22 是"视觉无损"的保守值；压缩率取决于素材复杂度，不取决于参数
  • 力气花在体积最大的那一项上

工程与验证

  • 源码与产物分离，并明确"改哪份"的约定
  • 无头浏览器 + CDP 读取页面状态，比截图更有信息量
  • 关键交互挂探针（window.__ended），区分"没触发"和"触发了但没生效"
  • 部署后回读线上内容做断言：字节数、特征串、逐资源状态码
  • 全屏遮罩必须有超时逃生路径，finish() 必须幂等
最后一句

这个项目里最难的不是"做出赛博朋克的感觉"——那只是审美和 CSS 的堆叠，调参数就行。 真正花时间的是让不可见的系统变得可见：视频到底播没播、事件到底触没触发、线上到底是哪一版。 视觉是门面，可观测性才是能交付的底气。
